# 本地优先、证据不足时使用 Wigolo 的外部验证设计

日期：2026-08-26
状态：对话设计已批准；书面规格待用户确认，尚未实施。

## 1. 已确认行为与范围

- Wigolo 独立服务，通过经过认证的 REST 与 PHP/GEOFlow 通信。
- 本地品牌知识足够则直接生成，外网请求为零。正文来源链接的存在不是重新抓取的理由。
- 本地不足才外部补充：有相关来源链接先 fetch，无合适链接再 search。
- 非核心事实无法验证：删除该断言后继续生成，保留删除原因，不改成无根据的模糊肯定。
- 核心事实无法验证或存在未解决冲突：保存待处理草稿，不自动采纳、发布或同步 WordPress。
- 本地资料的已验证状态沿用治理记录；本次提取来源链接不伪造实时核验日期。
- 不重新生成旧文章，不修改历史证据快照，不自动启用旧知识库，不运行全站采集。
- 不使用 Wigolo research/agent/answer，不新增自动知识库入库、定时同步、关键词分类或商品卡设计。
- 本期接入质量门禁链路：手动内容简报、quality_gated Task、批量导入创建的 quality_gated Task。legacy 引擎不暗中切换，启用此功能时提示改用质量门禁。

## 2. 现有代码约束

- `WorkerExecutionService` 在 brand_auto 模式把 reference_urls 清空，不能在新流程继续这样丢弃线索。
- `GenerationEvidenceSnapshotter` 当前禁止品牌模式显式外部证据、无本地命中时报错，且快照为 write-once。
- `ContentGenerationRequestService::reserve` 在事务中创建 run、保存本地证据并分发 database 队列；不得把网络调用塞进该事务。
- `ContentGenerationCoordinator` 用 lease/version 控制并发，编译前检查 required_fact_ids，现有校验不能被简单移除。
- `AdoptTaskDrivenGenerationRunsCommand` 自动采纳 ready_for_review；新的发布阻断必须在采纳和发布边界都执行，不能只靠 UI。
- `ReferenceEvidenceFetcher` 仅纯文本截断，不能把它的 HTTP 200/fetched 等同核验成功。
- 现有独立 database content-generation worker 继续消费；新增阶段不引入无人消费的隐藏队列。

## 3. 组成与责任

1. EvidencePreparationCoordinator：控制准备阶段、租约、预算、终态，所有质量门禁入口共用。
2. EvidenceCoverageAssessor：将标题、主题、核心问题、策略和蓝图转换为待支持的事实要求；对照本地片段判定覆盖。
3. ExternalEvidencePlanner：仅为缺口组织查询、URL 和域名范围，不把企业全文交给搜索引擎。
4. ExternalEvidenceProvider 接口与 WigoloRestClient：只提供 search/fetch/必要的商品 extract；统一错误和结构化响应。
5. ExternalEvidenceEvaluator：区分抓取可用性、来源适用性、片段对断言的支持/反驳/不足。
6. EvidenceCitationRenderer：依据最终采用的 evidence ID 输出真实来源链接，任务自动采纳和手动采纳共用。

现有本地检索保持品牌、来源站点、目录、语言及有效资料范围。关键词召回只产生候选，不等于证据足够。

## 4. 事实要求与判定

每条要求包含 stable claim_id、问题或候选断言、section_key、实体/商品 ID（如有）、core/optional、证据 ID、判定及理由。

- 蓝图明确 required_fact_ids 为强制核心要求，模型不能降级。
- 核心问题中不可缺的事实、特定商品身份/比较依据为核心；通用写作建议不强行变成需要外链的事实。
- 可删除而不影响标题承诺和核心问题回答的补充数字、旁证为非核心。
- 复用 GEOFlow 配置的文章模型做有 JSON schema 校验的覆盖评估与外部评估，记录模型/提示版本/用量；不配置第二套隐性模型供应商。
- 先规则过滤错品牌、错商品、缺正文、来源不适用，再让模型判断支持关系；每个“支持”必须绑定存在于证据中的原文摘录。
- 本地足够指核心和仍计划写出的非核心事实均获支持；明确删去的非核心要求不再触发搜索。
- 只有需要时效性事实且本地数据不满足该要求，才刷新。稳定知识不设置统一“每篇重验”。
- 输出格式错误、评估不可用不能当作通过；保留可用内容并进入待处理，避免外部搜索无限兜底。

## 5. 准备阶段与快照

保留现有请求时的本地快照为不可变初始证据，新增准备记录和最终证据清单；不编辑旧 run 的本地快照。

新 run 创建时冻结准备输入：品牌范围、标题/问题/关键词、策略/蓝图/预设版本、已选本地片段、参考 URL、检索策略及预算。

队列内在正文编译之前执行：

`local_check → external_fetch/search（按需）→ evidence_check → ready 或 draft_only`

外部调用在数据库事务外执行。短事务取得租约并保存阶段结果；提交时核对 lease token/version。重复执行复用已保存结果；不能重复追加证据或重复采纳。

新增准备记录以 run_id 唯一，含输入摘要、当前阶段、覆盖评估、查询日志、错误/删去的事实、截止时间、已用预算及 sealed_at。最终清单封存后禁止增加/替换证据；新增资料重试建立新 run，引用旧 run 作为前序。

外部抓取尝试与来源记录包含：原始 URL、最终 URL、标题、日期及是否推断、抓取时间、缓存年龄、抓取状态、正文文件/哈希、截断标识、采用片段及其上下文、支持的 claim_id、拒绝原因。原文存私有存储，不整篇塞进 Prompt 或日志。

外部记录独立标记 machine_assessed，不伪装成管理员审核的企业知识或 explicit reviewed evidence。进入正式证据表只允许准备服务的受控写入路径。

来源字段无 URL 的有效本地资料不一律禁止使用，但不能编造公开来源地址。

## 6. REST、来源策略与预算

Wigolo API 基址和凭证由部署配置提供，任务/表格不能传任意服务基址。

- search：query（最多 3 条针对缺口的查询），include_domains/exclude_domains、language/country、max_results=5、max_fetches=3、include_content=true、search_depth=balanced、citation_format=json；不设 format=answer。
- fetch：真实来源 URL、render_js=auto；仅在需要更新且缓存不满足时 force_refresh。
- 商品 extract 只补充有来源的结构字段；抓到图片不等于允许直接加入推广卡，保持已有商品确认机制。
- 每 run 总计最多 6 个唯一网页、最多 2 轮检索，外部阶段 180 秒硬预算；失败可对暂时性错误重试一次且计入预算，拦截不循环重试。
- 送模型的证据预算取模型实际可用上下文与配置上限的较小值，完整原文只用于留档；不得为塞入审计 JSON 而裁掉必要事实。
- 产品/价格/政策限定所选品牌已配置的官方域名，外部重定向也复核；通用科普可用按内容类型配置的可信来源域名。
- 品牌缓存键包含品牌/站点/来源策略及 URL；不通过全局 cache 工具把其他品牌的内容带入。公开通用材料仅在明确通用主题且通过来源策略时使用。
- 日期过滤不证明新品/热销，必须有对应商品上新/排行依据，不能把网页更新日期当商品上架日期。

## 7. 文章与发布

- 编译时使用封存的最终证据清单和本次有效蓝图，不修改用户原蓝图版本。
- 非核心缺口进入 prohibited_claims；生成时省略，后审查若又出现则仅允许一次受预算约束的修正；仍出现则保留待处理。
- 核心缺口不伪造 required_fact_ids 的满足状态。允许生成“仅已支持内容”的待处理草稿，并显示缺失章节/原因；必要时保存提纲和已有正文，不要求模型硬凑完整文章。
- 待处理内容保存在 run 草稿区，状态为 needs_evidence/manual_review_required；没有发布资格，不创建可供自动发布的 Article。
- 只有证据充分且通过现有质量门禁的 run 才进入 ready_for_review。采纳、审批和发布再次检查同一封存结果。
- 正文采用引用 ID，服务端验证 ID 存在且已采用后渲染 HTTPS/HTTP 来源链接。文末只列实际引用来源。
- 不把 Sources 章节当作蓝图正文多出的章节；在正文质量检查后统一追加，避免重复引用和章节数误判。
- 手动与自动采纳均执行引用完整性校验；WordPress 同步保留最终 HTML 链接。
- 抓取失败与事实不真实严格区分。无法获取不自动认定错误，不以低可信易抓网站降级放行。

## 8. 后台与兼容

- Task、Brief 增加外部补充策略 off/on_insufficient；旧记录迁移默认为 off，不追溯重新抓取。
- 新建质量门禁任务默认选择 on_insufficient；全局服务不可用时显式警告，不能显示“已启用且可用”。
- Bulk import 使用导入页统一默认策略，写入生成的 Task/Brief 并纳入分组/幂等摘要；无需新增必填 Excel 列。
- 页面展示阶段、缺失问题、查询词、来源、失败原因、被删除的非核心事实；技术审计与模型用量可展开。
- 服务不可用且本地足够仍可正常生成；本地不足则按核心/非核心规则结束，任务不无限进行中。
- 核心缺口暂停该 run 的自动推进，用户补资料后明确新建重试 run；定时调度不得为同一阻断选题无限重复消费模型。

## 9. 部署、安全与回滚

- 独立 Docker Compose 服务和私有数据卷，REST 认证，不暴露公网端口，不挂载宿主用户目录/浏览器登录态/企业数据库凭证。
- Wigolo 不需要读取整个企业知识库。只发送缺口问题及必要的公开实体信息，不发送个人订单、账号资料或 API Key 到搜索引擎。
- 网页内容不作为执行指令，不允许其更改来源策略、工具参数或提示约束。
- 请求 URL 的协议、私网/回环/link-local/元数据地址、DNS 和跳转安全检查必须覆盖 browser 子资源/WebSocket 等出站路径。内部 Wigolo REST 是配置受控例外，不等于允许抓取内网。
- 生产启用前以受控出站代理/网络隔离通过 SSRF 测试；不能仅凭应用第一次 URL 检查宣称浏览器安全。
- 独立 memory/CPU/并发上限、readiness 检查；database worker 启动与故障诊断随部署文档交付。
- 停用只禁止新外部调用，已有封存快照仍可使用；保留审计和草稿，禁止删除作为回滚手段。
- 保留许可证文件并核对 AGPL-3.0 使用义务。测试不推送生产站，不默认触发批量模型消费。

## 10. 验收

1. 所有三种质量门禁入口本地足够时：Wigolo 调用次数为 0，原来源 URL 可引用。
2. 本地缺一项事实只查该缺口；有相关 URL 时先抓取，不泛搜整个标题。
3. 品牌/商品不匹配证据被拒绝；通用科普来源可按策略使用。
4. HTTP 200 challenge、空正文、失败、超时、截断和过期缓存均可区分且不能直接标为验证成功。
5. 非核心缺口删去仍可生成；被删断言不能在修订中重新出现。
6. 核心缺口保留待处理草稿；自动采纳、审批/发布和 WordPress 同步均不能绕过。
7. 来源链接与实际支持片段对应；伪造 evidence ID/链接被拒绝；手动和自动采纳都生效。
8. 多次队列投递、失去租约、网络中断后重试不重复写快照或采纳；封存后保持不可变。
9. 提示预算不足有明确原因，模型用量记账，原始网页/审计不无界注入。
10. 内网/重定向/浏览器子资源 SSRF、HTML/XSS 与提示注入测试通过。
11. 现有 off 策略和历史 run 回归通过；不改变旧任务/文章/知识库治理状态。
12. 小批量真实测试覆盖兰亭商品/政策、第三方科普、拦截页面；报告实际成功/失败及成本，不凭上游宣传宣布可用。

## 11. 规格自审结论

已明确本地足够零抓取、无来源不必等于无证据、非核心删除/核心草稿、旧快照不可变、事务外联网、旧数据默认关闭、多入口一致性及服务禁用行为。正文缺口判断与来源抓取不是同一状态，相关性分数不作为事实真实性保证。未授权的生产发布、旧文章重写、全站采集和知识库自动扩充不在范围内。
